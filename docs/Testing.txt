

                                    Testing


Python project tests
--------------------

Run the Python tests from the repository root with::

  python3 -m pytest

Install the Python test runner separately from runtime dependencies::

  python3 -m pip install -r requirements.txt -r requirements-test.txt

The root ``pytest.ini`` deliberately limits default discovery to ``test/``.
This directory contains the SymCC-Parallel Python unit and integration tests.
The repository also vendors the upstream QSYM project below
``runtime/src/backends/qsym/qsym``; its Python tests require QSYM's separately
built PIN runtime and are therefore not part of an unqualified root invocation.

The discovery boundary does not ignore or disable QSYM tests. After satisfying
the prerequisites in the vendored QSYM README, run that suite explicitly::

  cd runtime/src/backends/qsym/qsym/tests
  python build.py
  python3 -m pytest -n auto

The GitHub Actions Python job uses ``util/python_test_gate.py`` rather than a
bare pytest command. The gate records required command/module/library
capabilities, enforces a historical collection floor, and fails on any test or
subtest skip, xfail, xpass, deselection, collection error, or ordinary test
failure. Its JSON artifact preserves skip reasons and makes environment-driven
coverage loss visible instead of accepting a green but reduced suite.

The job also requires the canonical node-id inventory in
``test/pytest-nodeids.json``. Unlike the numerical collection floor, this
detects removal or replacement of an existing test even when the total count is
unchanged. After an intentional test addition, removal, or rename, review the
collection diff and regenerate the inventory with::

  PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 PYTHONDONTWRITEBYTECODE=1 \
    python3 util/python_test_inventory.py \
    --output test/pytest-nodeids.json \
    --root test \
    --min-collected 1597

The generator always uses pytest collect-only mode, rejects deselection and
collection errors, sorts and deduplicates node IDs, and binds the resulting
list to a SHA-256 digest. Do not regenerate the file inside CI: its versioned
diff is the review boundary for intentional changes to test ownership. The CI
job and both test tools disable automatic third-party pytest plugin loading;
required plugins must be explicitly declared and enabled with ``-p``.

Manifest admission reads at most the configured limit plus one byte from a
single open descriptor before decoding or parsing. This binds the size check,
UTF-8 text, JSON object, and digest validation to one bounded snapshot rather
than a ``stat`` followed by a second path open. Duplicate JSON object members
are rejected even when their values are identical. Both tools force
``PYTEST_DISABLE_PLUGIN_AUTOLOAD=1``; an inherited empty or conflicting value
cannot silently change collection.


Live CGS tests
--------------

The Concrete Constraint Guided Scheduling slice has an independent exhaustive
predicate oracle, production continuation tests, persistent-restart tests, and
a synthetic mechanism benchmark::

  pytest -q test/test_live_cgs.py
  python3 benchmark/check_live_cgs_oracles.py
  python3 benchmark/benchmark_live_cgs.py \
    --distractor-instructions 500 --repeats 11

The oracle is the correctness gate. The benchmark measures target-order and
instruction-budget behavior only; it must not be cited as a public-target
coverage, bug-finding, completeness, or solver-speedup result.

Compiler tests
--------------


The short version:

$ ninja check


The slightly longer version:

We use the LLVM tools "lit" and "FileCheck", integrated with CMake. Since there
is little documentation on setting up the combination of those tools (apart from
the LLVM source code), here is an overview of the setup:

1. Tests are C or C++ source files in the "test" subdirectory of the project.
   They contain instructions for FileCheck in comments; see that tool's
   documentation.

2. We run the individual tests through lit, LLVM's configurable test runner. It
   finds each test file, performs some variable substitutions (see below), and
   runs the tests. The main source of configuration is "test/lit.cfg".

3. At configuration time, CMake creates an additional config file for lit,
   containing site-specific configuration such as the output directory of the
   build. The template is "test/lit.site.cfg.in".

4. CMake adds the "check" target, which invokes lit on the test suite. (It would
   be nice to call the target "test", but this is a reserved name in some
   versions of CMake, and the built-in test mechanism that it is reserved for
   doesn't track dependencies the way we need.)

Test files can use the following patterns:

%s             The test file itself.
%t             A temporary file.
%symcc         Invocation of clang with our custom pass loaded.
%filecheck     Invocation of FileCheck with the right arguments for the backend.

Since we support multiple symbolic backends, the tests must account for
different output from different backends. To this end, we rely on FileCheck's
prefix mechanism: test files use different prefixes to specify requirements on
different backends. The following prefixes are supported:

SIMPLE:   Active when we test with our own backend.
QSYM:     Active when we test with the QSYM backend.
ANY:      Always active.

The build system makes sure that "%filecheck" always expands to an invocation of
FileCheck that activates the right prefixes for the current build configuration.

Note that we run the tests only with the backend selected at configuration time,
so a full test requires building the project in multiple configurations. Also,
be aware that the backends write all log messages to standard error; therefore,
checks should not depend on the relative ordering of backend logs and messages
that the test program writes to standard output (use stderr instead).


                                Regression tests

In addition to the hand-written tests that exercise compiler functionality via C
code, we have a directory "test/regression" where we can collect LLVM bitcode
files that triggered bugs in real SymCC use. Generate the bitcode by running the
crashing compiler command with additional arguments "-emit-llvm -S -o-", pipe
the result through "opt -S -instnamer", and add a comment at the top to tell lit
how to compile it. The instruction naming is necessary because different LLVM
versions treat numbered (i.e., unnamed) instructions differently and may
complain if the numbering sequence doesn't match expectations.
