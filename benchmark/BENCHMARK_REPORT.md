# SymCC MPI 并行 Concolic Execution 基准测试报告

## 1. 测试方案

### 1.1 测试目标

评估 SymCC MPI 并行 concolic execution 框架在不同并行度下的：
- **吞吐量扩展性**：测试用例生成速率是否随 worker 数量线性增长
- **覆盖率有效性**：分支覆盖率是否随并行度提升而增加
- **多 master 架构**：高并行度下 multi-master hash 同步机制的正确性

### 1.2 测试对象

| 目标程序 | 库 | 源代码行数 | 种子数 | 种子类型 |
|---------|------|----------|--------|---------|
| png_read_fuzzer | libpng 1.2.56 | ~5,600 行 | 9 个 | RGBA, 灰度, 灰度+alpha, 调色板, 16bit, 32x32, 带 tEXt, 隔行扫描 |
| xml_read_fuzzer | libxml2 2.9.2 | ~数万行 | 15 个 | 基础 XML, CDATA, 命名空间, 深嵌套, 多属性, 注释, 混合内容, 自闭标签, 实体, UTF-8, 长文本, DTD, 数值 |

二进制文件使用 SymCC (基于 Clang/LLVM + QSYM 后端) 编译，确认包含 SymCC 插桩符号（png: 75 个 `__sym_ctor` 符号，xml: 139 个）。

覆盖率二进制使用 `gcc --coverage` 编译（`.gcno` + `.gcda` profile 数据）。

### 1.3 测试配置

- **并行度**: np = 2, 4, 8, 16, 32, 64, 128, 190（对应 1~185 workers）
- **每轮超时**: 300 秒（MPI wall-timeout = 265 秒，per-exec timeout = 30 秒）
- **架构**: np ≤ 46 单 master；np > 46 自动 multi-master（每 master 最多 45 workers）
- **覆盖率测量**: lcov 聚合 harness + 库目录，200K 分层采样上限
- **硬件**: AMD Threadripper PRO 9995WX (96C/192T), 250GB RAM, Ubuntu 24.04

### 1.4 MPI 并行架构

```
np ≤ 46:  Rank 0 = Master, Rank 1..N-1 = Workers
np > 46:  Rank 0..M-1 = Masters (auto-scaled), 其余 = Workers
          Masters 间通过 global_comm 做非阻塞 hash 同步
          每个 Master 组通过 group_comm (MPI Split) 隔离通信
```

工作流：
1. Master 导入种子文件 → 计算 SHA-256 hash → 写入 shared_dir
2. Worker 发送 TAG_READY → Master 分配 hash → Worker 从 shared_dir 读取输入
3. Worker 执行 SymCC → 输出原子写入 shared_dir → 仅将 hash 列表发回 Master
4. Master 去重后加入 pending_queue → 反馈给空闲 Worker 继续探索

## 2. 测试中遇到的问题及解决方法

### 问题 1: 覆盖率在所有并行度下完全相同（初始状态）

**现象**: 最初测试中，PNG 覆盖率在所有 np 下均为 77.3%，XML 均为 60%。

**根因**: 覆盖率测量使用 `gcov` 仅统计 harness 源文件（~30 行代码、~20 个分支），而非底层库（libpng/libxml2）。由于 harness 逻辑简单（读文件 → 调用解析函数），任何有效输入都能覆盖相同的 harness 分支。

**解决方法**:
- 实现 `_measure_with_lcov()` 函数，使用 `lcov --capture` 聚合 harness 目录 + 库构建目录的覆盖率数据
- 为每个目标创建 `.covlibdirs` 元数据文件，记录库构建目录路径
- 修改 `measure_coverage()` 路由逻辑：有 lib_dirs 时用 lcov，否则退化为 gcov

**涉及文件**: `run_benchmark.py` (新增 `_measure_with_lcov`, `_clean_gcda_files`, 修改 `measure_coverage`), `compile_public_benchmarks.sh` (生成 `.covlibdirs`)

### 问题 2: MPI 调用点未传递 lib_dirs 参数

**现象**: 修复后串行基线显示正确的 lcov 结果（PNG 9.1% line, 6.8% branch），但 MPI 并行仍显示旧的 gcov 结果（100% line, 77.3% branch）。

**根因**: `run_benchmark.py` 中有两处调用 `measure_coverage()` — 串行和 MPI 各一处。使用 `replace_all=true` 编辑时只替换了串行调用点，MPI 调用点因上下文不同未被匹配。

**解决方法**: 手动编辑 MPI 调用点（~第 1379 行），添加 `lib_dirs=cov_libdirs.get(target)` 参数。

### 问题 3: lcov 弃用选项警告

**现象**: `lcov` 报告 `lcov_branch_coverage` 选项已弃用。

**解决方法**: 全局替换 `lcov_branch_coverage=1` → `branch_coverage=1`。

### 问题 4: 种子多样性不足

**现象**: 修复覆盖率测量后，所有并行度下覆盖率仍然基本一致（~5%），且生成的测试用例文件大小只有 2-3 种，与种子文件大小完全吻合。

**根因**: 最初仅有 2-3 个基础种子。SymCC 的 concolic execution 只沿执行路径翻转单个分支条件，生成的变异体与输入仅差 1-3 字节。结构相同的种子只能探索相似的路径邻域。

**解决方法**:
- PNG: 新增 7 个多样种子（灰度、灰度+alpha、调色板、16bit、32x32、tEXt chunk、隔行扫描），共 9 个
- XML: 新增 12 个多样种子（CDATA、命名空间、深嵌套 20 层、多属性、注释+PI、混合内容、自闭标签、字符实体、UTF-8 多字节、长文本 500 字符、DTD、数值内容），共 15 个

### 问题 5: 尝试改进反馈循环（实验性，已回退）

**尝试的优化**:
1. **随机队列选择** — 用随机 dequeue 替代 FIFO，理论上防止早期种子后代占据所有 worker
2. **反馈限制** — 每次 SymCC 执行最多反馈 N 个新测试用例到队列（尝试 N=10 和 N=50）
3. **增加 per_exec_timeout** — 从 30s 提升到 90s

**实验结果**:
- 反馈限制 N=10: 覆盖率全面下降（PNG np=2: 16.7% → 14.7%），因为限制了总生成量
- 反馈限制 N=50: 仍然下降（PNG np=2: 16.7% → 15.4%）
- per_exec_timeout=90s: 每 worker 仅处理 ~3 个输入（原来 ~10 个），严重降低探索广度
- 随机队列: 引入不稳定性（PNG np=32 异常下降到 14.4%）

**结论**: 覆盖率平台期是 concolic execution 的固有特性，非反馈循环 bug。所有实验性改动已回退。

### 问题 6: LAVA-M 目标生成 0 个测试用例

**现象**: base64、md5sum、uniq、who 四个 LAVA-M 目标在所有并行度下均生成 0 个测试用例。

**状态**: 尚未确诊。这些二进制包含 SymCC 插桩符号（如 base64 有 72 个 `__sym_ctor`），但执行时 SymCC 未产生任何新输出。可能的原因包括：stdin/file 输入模式不匹配、QSYM 后端对 glibc 工具程序的兼容性问题、或运行时环境配置缺失。需进一步调试（如手动运行单个输入、检查 SymCC 日志输出）才能定位根因。此问题不影响 Google FTS 目标的测试有效性。

### 3.3 关键发现

**吞吐量线性扩展良好：**
- PNG: np=2 的 209 tc/s → np=32 的 4,736 tc/s（~23x，31 workers）→ np=64 的 8,183 tc/s
- XML: np=2 的 318 tc/s → np=32 的 9,287 tc/s（~29x，31 workers）→ np=128 的 19,780 tc/s
- 吞吐量在 np=64 附近开始饱和（受限于 MPI 通信开销和 hash 去重瓶颈）

**覆盖率在 np=2 时已接近饱和：**
- PNG: 种子基线 12.1% → np=2 跳升到 16.7%（+38%），之后 np=2~190 范围内仅波动 ±1%
- XML: 种子基线 4.0% → np=2 跳升到 7.4%（+85%），之后 np=2~190 范围内仅波动 ±1%
- 不同并行度间的覆盖率差异在 200K 采样噪声范围内（约 ±1.5%）
- 注：serial (种子) 基线为仅使用原始种子文件测量的覆盖率，未经 SymCC concolic execution 处理（串行 SymCC 执行在 300s 超时内未产生输出，ret=-1）

**去重唯一数在高并行度下反降：**
- PNG np=32 有 859K 唯一 → np=190 仅 389K 唯一
- 原因：np > 46 启用 multi-master 架构，master 间的 hash 同步为非阻塞异步操作，存在延迟窗口。在同步完成前，不同 master 组的 worker 会对相同输入重复探索，导致去重后唯一数反而下降
- 表明高并行度下 worker 间存在大量重复探索，而非 hash 碰撞

### 3.4 Hybrid AFL+SymCC 测试结果

在纯 concolic 覆盖率饱和后，集成 AFL++ fuzzer 进行 hybrid fuzzing 测试。
架构：AFL fuzzer (1 进程) + MPI SymCC workers (np-1 进程)，通过 `mpi_fuzzing_helper.py` 协同。

#### PNG Read Fuzzer (Hybrid vs MPI Concolic)

| 模式 | NP | AFL 生成 | SymCC+AFL 总数 | 分支覆盖率 | 覆盖率提升 |
|------|-----|---------|-------------|-----------|-----------|
| mpi | 2 | - | 52,153 | **16.7%** | +4.6% |
| mpi | 128 | - | 1,997,481 | **17.6%** | +5.5% |
| hybrid | 2 | 166 | 10,165 | **16.9%** | +4.8% |
| hybrid | 128 | 179 | 14,284 | **16.3%** | +4.2% |

PNG：Hybrid 与纯 concolic 覆盖率基本持平（±0.5%）。PNG 是二进制格式，AFL 的字节级变异和 SymCC 的符号约束求解探索类似的路径空间。

#### XML Read Fuzzer (Hybrid vs MPI Concolic) — 显著提升

| 模式 | NP | AFL 生成 | SymCC+AFL 总数 | 分支覆盖率 | 覆盖率提升 |
|------|-----|---------|-------------|-----------|-----------|
| mpi | 2 | - | 79,706 | **7.5%** | +3.5% |
| mpi | 128 | - | 5,265,589 | **7.7%** | +3.7% |
| **hybrid** | **2** | **3,549** | **28,160** | **10.7%** | **+6.7%** |
| **hybrid** | **128** | **3,513** | **399,710** | **10.6%** | **+6.6%** |

XML：**Hybrid 实现 10.7% 分支覆盖率，比纯 concolic 的 7.5-8.0% 提升约 35%**。AFL 生成结构多样的 XML 输入（~3,500 个），SymCC 对这些结构不同的输入进行符号执行，探索更多解析路径。Hybrid 在 np=2 时已接近最佳覆盖率，增加并行度不再有显著提升。

### 3.5 关键发现（更新）

**Hybrid AFL+SymCC 对结构化文本格式有效：**
- XML（文本格式）：Hybrid 覆盖率提升 35%（7.5% → 10.7%），因为 AFL 能生成结构多样的文本输入
- PNG（二进制格式）：Hybrid 无显著提升（16.7% → 16.9%），因为 AFL 对二进制格式的结构性变异能力有限
- AFL 的 bitmap 覆盖率（14%）远低于 lcov 分支覆盖率（17%），说明两种覆盖率度量的粒度不同

**SymCC 生成的测试用例不触发 AFL 新边覆盖：**
- 在所有 hybrid 配置中，`symcc_interesting=0`（afl-showmap 判定无新覆盖）
- 但 SymCC 的输出确实提高了 lcov 分支覆盖率（尤其是 XML）
- 这表明 AFL 的 edge bitmap 和 lcov 的 branch coverage 度量不同维度的代码覆盖

## 5. 结论

### 5.1 纯 Concolic Execution

SymCC MPI 并行框架的**吞吐量扩展性良好**（接近线性到 np=32），但**覆盖率不随并行度提升**。这是纯 concolic execution 的固有局限：

1. SymCC 只沿执行路径翻转单个分支条件，生成的变异体与输入仅差 1-3 字节
2. hash 唯一 ≠ 覆盖率不同 — 百万级 hash 不同的测试用例实际走的是同一组代码路径
3. 更多 worker 加速了路径邻域的穷举，但无法跨越到结构性不同的路径

### 5.2 Hybrid AFL+SymCC

集成 AFL fuzzer 后，覆盖率在**结构化文本格式上有显著提升**：
- XML: 分支覆盖率从 7.5-8.0% 提升到 **10.7%**（+35%）
- PNG: 无显著提升（二进制格式，AFL 变异能力有限）

Hybrid 模式的价值在于 **AFL 提供结构多样性，SymCC 提供约束求解精度**。
两者互补：AFL 快速覆盖"浅层"路径，SymCC 解决 AFL 难以突破的"深层"分支条件。
